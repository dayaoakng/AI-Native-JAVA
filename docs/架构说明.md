# 架构说明

> DDD Lite 是什么、与传统 MVC / 经典 DDD 的对比、解决了哪些问题，以及它如何与任何架构组合、开箱即用。

---

## 一、这是什么：单体优先的模块化架构

DDD Lite 是**单体（Modular Monolith）**架构——单进程、单部署单元，但内部按**业务域**切成清晰的模块与分层：

```
一个 Spring Boot 应用（单体）
└── modules/                        # 按业务域划分模块（不是按技术分层）
    ├── partner/                    # 伙伴域：interfaces / application / domain / infrastructure
    ├── order/                      # 订单域
    └── ...
```

**关键定位**：它不是一个"微服务框架"，也不是"又一个 DDD 全家桶"。它是一个**单体项目内部的代码组织规范**：

| 维度 | 说明 |
|------|------|
| 部署形态 | **单体**（单进程、单数据库、单 jar） |
| 内部组织 | **模块化**（按业务域 + 四层结构，边界清晰） |
| 与微服务的关系 | **互不冲突**——它解决的是"一个进程内代码怎么写"，不解决"进程怎么拆" |
| 组合能力 | **可与任意架构组合**——嵌套进微服务的一个服务、嵌进网关、嵌进已有 Spring 项目皆可 |

---

## 二、传统 MVC 架构的问题

传统 `Controller → Service → Mapper` 三层（贫血模型）在中小项目够用，但随业务增长会出现几个典型问题：

| 问题 | 表现 |
|------|------|
| **上帝类 Service** | 业务逻辑全塞进 `XxxService`，动辄上千行，改一处崩全局 |
| **贫血模型** | `Entity` 只有 getter/setter，业务规则散落在 Service 各处，同一状态多处在改 |
| **假分层** | 名义上有分层，实际 Controller 里写业务、Service 里拼 SQL，层形同虚设 |
| **测试难写** | 业务规则和数据库/框架耦合，不连库测不动，只能写集成测试 |
| **AI 不可控** | 没有边界约束，AI 生成代码时"自由发挥"，每次换模型风格就变 |

**根因**：三层 MVC 没有规定"每层只能做什么、一个类多大、业务规则放哪"，边界靠自觉，必然失守。

---

## 三、DDD Lite 解决了什么

对应上面的问题，DDD Lite 用**硬规则**把边界钉死：

| MVC 的问题 | DDD Lite 的答案 |
|------------|-----------------|
| 上帝类 Service | **1 用例 = 1 Handler（≤100 行）**，物理隔离，改一个不碰另一个 |
| 贫血模型 | **充血 Entity**：业务规则长在实体上，状态只有一条变更路径 |
| 假分层 | **依赖单向 + 机器门禁**：分层违规直接扫描拦截 |
| 测试难写 | **domain 层无框架**：业务规则纯单元测试，秒级跑完 |
| AI 不可控 | **硬规则 + 决策树 + 自动检查**：AI 查表写码，输出稳定可审查 |

核心思想只有一句：**把资深工程师脑中的判断，翻译成机器可检查的规则**。

---

## 四、DDD Lite vs 传统 MVC vs 经典 DDD

| 维度 | 传统 MVC（贫血） | 经典 DDD | **DDD Lite（本方案）** |
|------|------------------|----------|------------------------|
| 业务规则位置 | 散落在 Service | 聚合根 / 领域服务 | **充血 Entity** |
| 用例组织 | 一个 Service 一堆方法 | 应用服务 + 领域服务 | **1 用例 = 1 Handler** |
| 实体模型 | 贫血（纯 POJO 映射） | 聚合根 + 实体 + 值对象 | Entity + ValueObject（不造 Aggregate） |
| 分层 | 3 层，易假分层 | 复杂，概念多 | 4 层，依赖单向 |
| 学习成本 | 低 | 高（概念多） | **中低**（砍掉多余抽象） |
| 对 AI 友好 | 差（无边界） | 差（抽象太多 AI 易错） | **好**（决策树直接查表） |
| 适用规模 | 小项目 | 复杂核心域 | **中小到大型单体** |

**一句话**：DDD Lite 保留 DDD 的核心价值（充血模型、分层、领域边界），砍掉让 AI 和人都犯迷糊的抽象（聚合根、领域服务、Event Sourcing 等）。

---

## 五、优点

1. **边界清晰，可审查可交接**：每一层职责固定、命名即语义，新人/新 AI 一看就懂。
2. **可测试**：业务规则集中在充血 Entity，纯单元测试秒级跑完，不依赖数据库。
3. **AI 友好**：硬规则 + 决策树 + 自动检查，AI 输出稳定、可量化、可门禁。
4. **务实**：不追求 DDD 形式完整，只保留能产生真实价值的部分，落地成本低。
5. **单体易运维**：无分布式复杂度（无服务发现、无分布式事务、无 RPC 调试），部署简单。

---

## 六、缺点与边界（如实说明）

1. **不解决"进程拆分"问题**：它是单体内部规范，不提供微服务的拆分、熔断、服务治理等能力。
2. **强规则有纪律成本**：1 用例 1 Handler 会带来更多类文件，团队需要接受"多而小"的组织方式。
3. **需要门禁配套**：规则若没有扫描脚本 + CI 兜底，靠自觉会失效——好在脚手架已内置。
4. **跨模块协作有限**：Port + 事件的松耦合适合中等规模；超大单体最终仍需拆微服务（届时可按模块切出）。
5. **生产数字未开源可复算**：README 中的 462 Handler 等指标来自内部生产系统（BOSS），其源码未开放；但**口径已开源**——`scripts/standards/metrics.py` 可对任何仓库跑出同样口径的统计，`scaffold/` 作为最小可复现样本。

---

## 七、与微服务的关系：不冲突，可组合

DDD Lite **不影响、也不替代**微服务架构，它与任意架构组合：

| 组合场景 | 方式 |
|----------|------|
| 独立单体项目 | 直接以本骨架为起点，开箱即用 |
| 微服务中的单个服务 | 每个服务内部用 DDD Lite 组织代码（推荐） |
| 已有 Spring 项目改造 | 新功能按规范写，老代码渐进式替换（见开发手册 §十一） |
| 单体 → 微服务演进 | 模块边界清晰，未来按 `module` 切出即可独立成服务 |

**为什么推荐"微服务里也用它"**：微服务只解决了"服务之间"的边界，**服务内部**的代码如果还是上帝类 Service + 贫血模型，微服务带来的复杂度只会放大烂代码的代价。DDD Lite 补的正是"服务内部"这一层。

---

## 八、开箱即用

1. 复制 [`scaffold/`](../scaffold/) → 全局替换包名/groupId → 直接开发
2. 自带 H2 内存库，`mvn spring-boot:run` 一键启动，无需任何外部依赖
3. 自带合规扫描 + pre-commit hook + CI 门禁，规则落地零配置

> 一句话总结：**DDD Lite 是"单体项目内部的架构规范"——管好一个进程内的代码怎么写，与微服务正交、可任意组合、开箱即用。**
