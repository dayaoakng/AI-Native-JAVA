## 一、演进主线

```
贫血模型 + Service（起点）
        │  阶段 1：新模块直接按 DDD Lite 标准开发
        ▼
Handler 接线 + Entity 充血（口径 A）
        │  阶段 2：领先模块细化领域边界
        ▼
消 Service / 消 Aggregate / 消 domain-service
        │  阶段 3：落后模块逐批重构
        ▼
DDD Lite 目标态（全模块 L2/L3）
```

## 二、遗留代码分级策略

| 场景 | 策略 |
|------|------|
| 小改（< 10 行） | 保持原样，不强行引入 Handler |
| 中改（10–50 行） | 局部优化：把业务逻辑下沉到 Entity 方法 |
| 大改（> 50 行） | 重构为 Handler + Entity |

## 三、Service 删除清单（删除前必须完成）

1. 创建对应 Handler（读写都要）
2. Controller 切到 Handler
3. 单元测试通过
4. 集成测试通过
5. 检查是否被其他模块调用
6. 跨模块调用先用事件/Port 解耦
7. 确认后删除 Service
8. 删除 ServiceImpl
9. 删除对应测试文件

无法立即删除时：`@Deprecated` 标记 + 登记 TECHNICAL-DEBT + 必须批准保留。

## 四、模块优先级（现状）

| 优先级 | 对象 | 状态 |
|--------|------|------|
| P0 | 全业务模块接线 + 假 Handler 清零 | ✅ 已完成 |
| P1 | 裸 entity 长尾迁移（TD-007） | ✅ 已完成（W0–W4） |
| P2 | Handler > 100 行清零（TD-012） | 🔄 剩 ~15 个 |
| P3 | 厚 Adapter 触达制 | 🔄 进行中 |
| DEFER | ledger / external / ops 接入 admin | ⏸️ 待产品确认 |

## 五、演进约束（每步都须遵守）

- 规范先行：新功能按 AI-RULES 写 Handler + Entity，**不因旧代码未达标而降低新代码标准**。
- 冲突优先级：`AI-RULES.md` > `MODULE-MATURITY.md` > 其他文档。
- 提交兜底：pre-commit hook 自动拦截命名/行数/BOM/service 违规（`git config core.hooksPath scripts/githooks`）。
- 合规扫描：`scripts/standards/scan-compliance.py`。
