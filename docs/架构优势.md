# 架构优势

> 承载「AI 开发规范」的架构选择，以及它在一个 20+ 模块物联网卡运营平台上的真实成效。

---

## 一、我们选择了什么：DDD Lite

经典 DDD（领域驱动设计）强大但复杂——聚合根、实体、值对象、领域服务、仓储……概念多、上手慢，**尤其不适合 AI 生成代码**（抽象层次越多，AI 越容易张冠李戴）。

所以我们做了一个务实的取舍，叫 **DDD Lite**：

| 项目 | 经典 DDD | DDD Lite（我们） |
|------|----------|-----------------|
| 聚合根 | 单独的 Aggregate 类 | **Entity 类**直接担当 |
| 包结构 | `domain/aggregate/` | `domain/entity/` |
| 术语 | Aggregate / Entity / ValueObject | Entity / ValueObject |

**一句话**：保留 DDD 的核心价值（充血模型、分层、领域边界），砍掉让 AI 和人都犯迷糊的抽象。

---

## 二、四大架构支柱

### 支柱 1：充血模型（业务规则长在实体上）

业务规则不散落在 Service，而是**集中在 Entity 内部**，以方法的形式表达：

```java
public class PartnerEntity extends BaseEntity {
    public void activate() {
        if (this.status == 1) throw new BusinessException("已激活");
        this.status = 1;
    }
    public boolean canSettle() { return this.status == 1; }
}
```

**优势**：
- 状态转换只有一条路径，不会出现「A 处改 status=1，B 处又改 status=2」的不一致
- 业务规则可**纯单元测试**，不依赖数据库，跑得飞快
- 一个实体管一件事，内聚

### 支柱 2：一个用例一个 Handler（消灭上帝类）

```java
@Component
@RequiredArgsConstructor
public class ActivatePartnerHandler {
    private final PartnerRepository partnerRepository;
    private final ApplicationEventPublisher eventPublisher;

    @Transactional
    public PartnerResponse execute(Long partnerId) {
        PartnerEntity partner = partnerRepository.requireById(partnerId);
        partner.activate();                    // 业务逻辑在 Entity
        partnerRepository.save(partner);
        eventPublisher.publishEvent(...);      // 跨模块通知
        return PartnerAssembler.toResponse(partner);
    }
}
```

**优势**：
- 每个用例 ≤ 100 行，一屏读完，审查快、交接快
- 用例与用例之间**物理隔离**，改一个不碰另一个
- 天然可测试：mock 仓储，验证编排

### 支柱 3：分层依赖单向（外向内，永不反向）

```
interfaces（接口层）   Controller / Request / Response / VO
        ↓
application（应用层）  Handler / Assembler / Support
        ↓
domain（领域层）       Entity / ValueObject / Repository(接口) / Event / Port
        ↑ 实现
infrastructure（基础设施层） Mapper / PO / RepositoryImpl / MQ / Cache
```

**优势**：
- domain 层不依赖 Spring/MyBatis/Redis，**纯业务、可移植、可独立测试**
- 换数据库、换框架，只动 infrastructure，核心业务不动
- 依赖方向单一，AI 和人都不会写出「循环依赖」的烂代码

### 支柱 4：跨模块走 Port / 事件（松耦合）

模块之间**禁止**直接 `@Autowired` 别人的 Service/Mapper，只允许两条路：

- **异步**：领域事件 `publishEvent` → 对方 `@EventListener`
- **同步**：Port 接口（调用方定义契约，提供方实现）

**优势**：
- 模块可以独立演进、独立部署
- 加一个下游模块，不用改上游代码
- 依赖关系清晰，一查便知「谁依赖谁」

## 三、真实成效（来自 20+ 模块的生产系统）

这套架构不是纸面设计，而是已经在一个物联网卡运营平台（含订单、库存、计费、返佣、客户、流量等 20+ 业务模块）上落地并跑通的。实测结果：

| 指标 | 结果 |
|------|------|
| 业务模块 Handler 总数 | **462 个** |
| HandlerSpec（单元测试） | **174 个** |
| 假 Handler（空壳转调 Service） | **0** |
| 遗留 ApplicationService | **0** |
| 遗留 DomainService | **0** |
| `XxxAggregate` 类 | **0** |
| `domain/service/` 包 | **0** |
| Controller 直调 Handler（口径 A） | **近 100%** |

**翻译成人话**：一个 20+ 模块的系统，**没有上帝类、没有贫血模型残留、没有假分层**——每一层都在真实工作，每一个用例都清晰可查。

---

## 四、这个架构解决了哪些痛点

| 传统项目的痛 | 我们的答案 |
|--------------|-----------|
| Service 越写越大，改一处崩全局 | 1 用例 = 1 Handler，物理隔离 |
| 业务逻辑散落各处，测试写不动 | 充血 Entity，规则集中、可单测 |
| 模块互相依赖，牵一发动全身 | Port + 事件，边界清晰 |
| AI 生成代码质量飘忽 | 硬规则 + 决策树，输出稳定 |
| 代码量膨胀，审查成本失控 | 单文件/单方法硬上限，强制拆分 |
| 换人接手困难 | 命名即语义 + 统一分层，一看就懂 |

---

## 五、为什么这套架构「值得推广」

1. **务实**：不追求 DDD 的形式完整，只保留能产生真实价值的部分。
2. **AI 原生**：每一步设计都在降低 AI 的决策成本，天生适合「AI 写、人审」的新范式。
3. **已验证**：有生产系统背书，不是 demo。
4. **可复制**：`scaffold/` 可直接启动，新项目零门槛复用。

> 一句话总结：**我们不是「用了 AI」，而是「为 AI 设计了一套架构」——让 AI 成为稳定产出，而不是不稳定因素。**
