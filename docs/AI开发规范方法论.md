# AI 开发规范方法论

> 一套让 AI 稳定写出可维护、可交接、可落地的企业级 Java 后端的规则体系。

---

## 一、先说问题：为什么大多数团队「AI 写不好业务代码」

不是因为模型不够强，而是因为**没有给 AI 一个可执行的规则**。于是出现了三个经典翻车现场：

| 翻车现场 | 根因 |
|----------|------|
| AI 把业务逻辑写进 Controller，三行代码里夹着 SQL | 没有规定「每一层只做什么」 |
| AI 建了 2000 行的 `OrderService`，越改越大 | 没有规定「一个类最多多大、什么时候必须拆」 |
| 每换一个模型，代码风格就变一次，交接成本爆炸 | 没有「不因模型而变」的统一契约 |

**结论**：AI 生成代码的质量，取决于你给它定义的边界有多清晰。规则越硬，AI 越不会「自由发挥」。

---

## 二、我们的解法：把「工程判断」固化成「硬规则」

我们做的事情只有一件——**把资深工程师脑中的判断，翻译成 AI 必须无条件遵守的、可检查的规则**。

### 2.1 五条硬规则（违反即拒绝生成代码）

| # | 规则 | 解决什么问题 |
|---|------|-------------|
| 1 | 禁止新增 `service/`、`XxxService`、`XxxApplicationService` | 消灭「什么都往里塞的上帝类」 |
| 2 | 文档必须带可追溯元数据 | 每一份设计/计划都能查到「谁、何时、为何」 |
| 3 | 单文件 ≤ 300 行，Handler ≤ 100 行，方法 ≤ 30 行 | 强制拆分，杜绝巨型文件 |
| 4 | 领域实体必须进 `domain/entity/`，禁止裸 `entity/` | 对象各归其位，不因「方便」乱放 |
| 5 | 源码 UTF-8 无 BOM | 消灭编码导致的编译/CI 事故 |

### 2.2 关键：这套规则是「可自动检查的」

规则如果不能自动检查，就只是口号。我们的每条硬规则都对应了**机器检查手段**：

- 命名/行数/BOM/`service/` 违规 → **pre-commit hook + CI 双门禁自动拦截**
- 合规扫描 → `scripts/standards/scan-compliance.py` 一键出报告（本仓库已内置，纯标准库、零依赖）
- 假 Handler / 僵尸 Handler → 静态扫描识别并登记技术债务

**这正是「AI 开发」和「人肉开发」的本质区别**：人的规范靠自觉，AI 的规范靠**可执行的门禁**。

## 三、给 AI 的「决策树」，而不是「建议」

我们不给 AI 讲大道理，而是给一张**它可以直接走流程的决策树**：

```
这段代码是什么？
├── 领域规则（状态校验/变更、业务计算、不变量维护）
│   └── 写入 domain/entity/、domain/valueobject/
├── 用例编排（加载实体、调仓储、跨实体协作、事务、发事件）
│   └── 写入 application/handler/，一个用例一个 Handler
├── 持久化抽象
│   └── 接口写 domain/repository/；实现写 infrastructure/
├── 跨模块协作
│   └── 用 domain/event/ 或 domain/port/
├── 外部适配（MyBatis/Redis/HTTP/MQ）
│   └── 写入 infrastructure/
└── 接口层参数/返回值
    └── 写入 interfaces/request|response|vo/
```

以及「对象落位」决策树：

```
这个对象有没有独立身份、状态、业务行为？
├── 有 → 领域实体 domain/entity/XxxEntity
└── 没有
    ├── 不可变业务概念（金额/编号）？→ domain/valueobject/
    ├── 只是数据库映射？→ infrastructure/（XxxPO / XxxRow）
    └── 只是 HTTP/消息契约？→ interfaces/（Request/Response/VO）
```

**效果**：AI 不再「猜该放哪」，而是「查表」。输出稳定、可预期。

## 四、这套方法论带来什么

### 4.1 对团队

- **AI 输出可信**：同一套规则下，任何模型写出的代码结构一致，可审查、可交接。
- **新人/新模型零成本对齐**：不用「口口相传」，规则就是文档。

### 4.2 对代码

- **可维护**：单文件、单方法都有上限，任何一段代码都能在 30 行内读完一个方法。
- **可测试**：业务规则集中在充血 Entity，可用纯单元测试覆盖，不依赖数据库。

### 4.3 对交付

- **进度可度量**：Handler 数量、假 Handler 数、口径 A 接线率……每个指标都可扫描、可量化。
- **质量有门禁**：违规代码在 commit 阶段就被拦下，不会流入主分支。

---

## 五、这套规范为什么「AI 友好」

我们的设计里，有一条贯穿始终的原则：**降低 AI 的决策成本**。

| 设计决策 | 为什么对 AI 友好 |
|----------|-----------------|
| 一个用例一个 Handler | 上下文小，AI 生成准确率从「100 行内 85%」起跳，越超长越崩 |
| 聚合根 = Entity，不做 Aggregate | 少一层转换，AI 不需要理解「聚合根 vs 实体」的抽象 |
| 充血 Entity | 业务规则集中在实体，AI 只需在 Entity 里找/写规则 |
| 命名即语义 | 类名直接告诉 AI 它的职责与位置 |
| 硬规则可自动检查 | AI 写完能立刻自检，错了能立刻改 |

> 这不是「为了架构而架构」，而是**每一步都在替 AI 消除歧义**——歧义越少，AI 越不会瞎编。

## 六、你可以怎么用

1. 看 [架构优势](架构优势.md) 了解这套规范落在一个真实系统上的效果。
2. 把 `AGENTS.md` / `.cursor/rules/ddd-lite.mdc` 复制进你的项目，AI 编程助手立即按规则执行。
3. 拿 `scaffold/` 直接 `mvn clean install` 跑一遍，看最小样例长什么样。
4. 跑 `python scripts/standards/scan-compliance.py --root scaffold`，看这套规则如何被机器检查。
5. 把这套规则移植到你的团队——它不绑定语言细节，核心是「硬规则 + 决策树 + 自动检查」三件套。
